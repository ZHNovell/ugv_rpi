# UGV Robot на Orange Pi 4 Pro — Концепция и дорожная карта

* **Версия:** 1.1
* **Последнее обновление:** 2026-10-19
* **Платформа:** Orange Pi 4 Pro (Allwinner A733, NPU 3 TOPS) + General Driver for Robots (ESP32) + шасси WAVE ROVER + 2-Axis Pan-Tilt (ST3215) + лидар D500 + AX-M1

---

## 1. Видение проекта

**Цель:** создать полуавтономную → автономную мобильную робототехническую платформу, которая умеет:
* Воспринимать окружение в реальном времени (зрение + лидар)
* Строить карту помещения (SLAM) и навигироваться по ней
* Распознавать людей, позы и жесты
* Демонстрировать автономное поведение (патруль, слежение, исследование)

**Позиционирование:** не «игрушка», а учебная, расширяемая и презентабельная система. Главная ценность — замкнутый цикл «восприятие → решение → действие» и глубокая интеграция железа и софта.

**Принципы:**
* Максимально использовать NPU (YOLO-серия)
* Модульность: каждая функция включается независимо
* Все ключевые решения документировать
* **Гибридный подход:** точечные библиотеки без ROS2 (ROS2 — опционально)
* Опираться на открытую экосистему (Ultralytics, примеры Waveshare, OpenCV)

**Ключевые решения:**
* **4 NPU-сервера** через UNIX-сокеты: `npu_server` (YOLO26s), `npu_pose_server` (YOLO11_pose), `npu_seg_server` (YOLO11_seg), `npu_depth_server` (YOLO26n_depth).
* **ArUco** — через OpenCV (CPU), не NPU.
* Видео через GStreamer `tee` — превью и запись одновременно.
* CV-режимы переключаются JSON-командами (`{"T":10304}` = OBJECTS, `{"T":10309}` = MP POSE, `{"T":10310}` = DEPTH, `{"T":10311}` = SEG, `{"T":10312}` = ARUCO).

### 3.2 Целевая (план)

**Основной подход — гибридный (без ROS2).** Точечно интегрируем **ключевые библиотеки**, не тащим **весь ROS2-стек** (DDS, ноды, launch-файлы — **избыточны** для edge-платформы и **съедают CPU**).

**SLAM (без ROS2):**
- **Hector SLAM** (лёгкий порт) или **свой** SLAM на Python/C++.
- Данные лидара D500 → напрямую в `cv_ctrl.py` (драйвер `ld19`/`stl19p`).
- Данные энкодеров ESP32 → одометрия в Python.

**Навигация (без ROS2):**
- **VFH** (Vector Field Histogram) или **Bug-алгоритм**.
- Лидарная защита: при `< 0.25 м` — стоп (`{"T":1,"L":0,"R":0}`).
- Замедление: при `< 0.5 м`.

**Sensor Fusion (лидар + depth):**
- `npu_depth_client.py` → матрица глубины.
- Лидар D500 → массив полярных координат.
- **Python-воркер** в `cv_ctrl.py` объединяет → **Occupancy Grid**.
- **Canvas** в вебе через **Socket.IO** (не rosbridge).

**ROS2 — опционально:**
- Если **понадобится** сложный SLAM (например, **Cartographer** для **больших** помещений).
- **Docker** + **только** нужные ноды.
- **Не сейчас.**

## 4. Стратегия моделей: постоянные vs по требованию
Оркестрация двух NPU (A733 + AX-M1)
A733 NPU: легкие, постоянные задачи (YOLO26s детекция).
AX-M1 NPU: тяжелые, запускаемые по требованию задачи (YOLO26_depth, YOLO26_seg, YOLO26_pose).

### 4.1 Постоянные NPU-серверы



| Сервис | Модель | Сокет | Статус |
| :--- | :--- | :--- | :--- |
| `npu-server.service` | YOLO26s (детекция) | `/tmp/npu11.sock` |  Работает |
| `npu-pose-server.service` | YOLO11_pose (поза) | `/tmp/npu_pose.sock` |  Работает |

* **Плюсы:** нет задержки загрузки, мгновенное переключение.
* **Минусы:** потребление памяти (50–100 МБ на модель), конкуренция за NPU - решено переключением.

### 4.2 По требованию

| YOLO26s-depth | Оценка глубины | Постоянно (в навигации) | Нужна для Sensor Fusion с лидаром и Seg |
| YOLO26s-Seg | Сегментация | По требованию (при обнаружении объекта) | Для границ объектов и Semantic Depth Fusion |
| YOLO26s_pose | Позы | По требованию (демо, игра) | Не в автономной навигации |
**Реализация:**
* Новые `npu_depth_server` и `npu_seg_server` (отдельные systemd-сервисы).
* По умолчанию не запущены.
* Запуск через кнопку в веб-интерфейсе или JSON-команду (`systemctl start / stop`).
* *Альтернатива:* один NPU-процесс с динамической загрузкой `.nb` файлов (технически сложнее).
* *Рекомендация:* начать с отдельных сервисов. 12 ГБ RAM гарантированно хватит на 3–4 модели одновременно.


### 4.3 Sensor Fusion (лидар + depth)

**Проблема:** лидар «слепнет» перед стёклами, зеркалами, прозрачными поверхностями.

**Решение:** объединять **лидар** и **depth** в **Python-воркере** (`cv_ctrl.py`).

**Алгоритм:**
1. `npu_depth_client.py` → матрица глубины (16×16 + near-RLE).
2. Лидар D500 → массив полярных координат (расстояния по углам).
3. **Воркер** сопоставляет:
   - Если лидар **видит** препятствие — берём **его** данные.
   - Если лидар **не видит** (стекло) — берём **depth**.
4. **Occupancy Grid** → Canvas в вебе (Socket.IO).

**Формат:** JSON → `{"grid": [...], "near_rle": [...], "lidar": [...]}`.

**⚠️ Потенциальное узкое место:**
- **Sensor Fusion** может стать **бутылочным горлышком** (Python **медленнее** C++).
- **Если** производительность **упадёт** (например, **< 10 FPS** при fusion) — **переписать** модуль на **C++** или **Cython**.
- **Cython** — **проще** (Python-совместимый синтаксис, **компилируется** в C).
- **C++** — **быстрее**, но **сложнее** интегрировать (нужен **pybind11** или **C-API**).
- **Решение:** **сначала** Python (простота). **Если** упрёмся — **Cython** (компромисс). **Потом** — **C++** (если нужно).

### 4.4 Semantic Depth Fusion (Seg + Depth)

**Проблема**: лидар даёт 2D-расстояния, но не знает, **что** за объект. Depth-модель даёт карту глубины, но не знает **границ** объекта. Вместе они дают **точное расстояние до объекта** (например, до человека).

**Решение**: объединять маску сегментации (`YOLO26s-Seg`) и карту глубины (`YOLO26s-Depth`) в Python-воркере (`cv_ctrl.py`).

**Алгоритм**:
1. `YOLO26s-Seg` → маска объекта (полигон).
2. `YOLO26s-Depth` → матрица глубин (768x768, интерполируется до размера кадра).
3. Накладываем маску на карту глубины → берём **медиану** глубин под маской (устойчива к шумам и краям).
4. Получаем `{class_name, bbox, distance (м), center_x, center_y}`.

**Где работает**: обе модели — на **AX-M1** (Radxa AICore). `YOLO26s` (детекция) — остаётся на **A733**.

**Использование**:
- **Защита**: если `distance < 0.4 м` — стоп (`{"T":1,"L":0,"R":0}`).
- **FOLLOW**: держать дистанцию `1.5 м` до `person` — пропорциональное управление скоростью.

**Производительность**: нейросети — на AX-M1 (не грузят CPU). Python — только `np.median` и `cv2.resize` — 2-3 мс на кадр.

**Зависимости**: `numpy`, `cv2` (уже есть в `ugv-env`).

### 4.5 Лидарная защита

**Функция:** мгновенная остановка при **опасном** сближении.

**Алгоритм:**
- Лидар D500 → расстояния по углам (360°).
- **Фронтальный сектор** (±30°) → минимальное расстояние.
- Если `< 0.25 м` → **стоп** (`{"T":1,"L":0,"R":0}`).
- Если `< 0.5 м` → **замедление** (масштаб скорости × 0.5).

**Реализация:** функция в `app.py` или `cv_ctrl.py`, вызывается **каждый** кадр.

## 7. Ключевые решения и открытые вопросы

### 7.1 Что необходимо решить
1. **ROS2 vs собственный стек.** ROS2 **избыточен** для edge-платформы (DDS, ноды, launch — **съедают CPU**). 
**Решение:** **гибридный** подход — **точечные** библиотеки (Hector SLAM, VFH) **без** ROS2. 
2. **ROS2 — опционально**, если **понадобится** сложный SLAM (Docker + только нужные ноды).
3. **Лидар D500.** Подключение выполняется через USB-UART переходник.
   * *Решение:* Использовать готовые драйверы `ld19` / `stl19p` для ROS2.
4. **PT-стабилизация.** 
   * *Решение:* Передавать данные с IMU (через ESP32) напрямую на сервоприводы для динамического удержания горизонта камеры.

### 7.2 Анализ рисков

| Риск | Метод митигации (снижения риска) |
| :--- | :--- |
| **Перегрузка NPU** при одновременном запуске 4 моделей | Динамическая загрузка тяжелых моделей (depth/seg) строго по требованию. |
| **Баг eMMC CQE** | Проблема уже решена программно (зафиксировано на 150 МГц), перенесено на NVMe. |
| **Высокая нагрузка от ROS2** | **гибридный** подход — **точечные** библиотеки (Hector SLAM, VFH) **без** ROS2. |
| **Лидар «слепнет» перед стёклами** | Настроить Sensor Fusion: объединять данные лидара с картой глубины от depth-камеры. |
| **Seg + Depth**: рассинхрон кадров | Обе модели обрабатывают один и тот же кадр (640x640). Синхронизация — через общий буфер в `cv_ctrl.py`. |


### 8. Блокнотик (Инженерный бэклог архитектурной оптимизации на рассмотрении и оценке).

1. **Узкое место: Архитектура межпроцессного взаимодействия (IPC)**

• **Проблема:** Сейчас работают 4 независимых NPU-сервера через UNIX-сокеты. На этапе 4, когда добавится Semantic Depth Fusion, потребуется передавать кадры высокого разрешения (или тяжелые маски/тензоры) между сервисами (npu_seg_server и npu_depth_server) в cv_ctrl.py.
• **Риск:** Передача сырых картинок или больших массивов через сокеты создает огромную нагрузку на CPU из-за постоянного копирования данных в памяти (context switching).
• **Решение:** Вместо UNIX-сокетов для передачи тяжелых данных (кадров) использовать разделяемую память (Shared Memory) через POSIX shared memory или библиотеки типа multiprocessing.shared_memory в Python. Через сокеты передавать только сигналы/метаданные (например, JSON с координатами или уведомление «кадр в буфере №1 готов»).

- `multiprocessing.shared_memory` — встроено в Python 3.8+, ничего ставить не надо. Но **нюанс**: при использовании shared_memory нужно самостоятельно управлять жизненным циклом (создание/удаление), иначе будут **утечки** памяти.

2. **Производительность Python на этапе Sensor Fusion**

• **Проблема:**  «Сначала Python (простота). Если упремся — Cython, потом C++».
• **Риск:** Интерполяция карты глубин 768x768 до размеров кадра, наложение масок сегментации и расчет np.median для нескольких объектов в секунду на Python быстро упрутся в GIL (Global Interpreter Lock). Теряем FPS не на NPU, а на подготовке данных.
• **Решение:** Не терять время на чистый Python для блочной интерполяции и маскирования. Сразу писать уже после окончания тестов шасси и привода этот модуль с использованием векторизации NumPy (которая под капотом работает на C) или использовать функции OpenCV (cv2.resize, cv2.bitwise_and), которые эффективно используют многопоточность процессора. К Cython/C++ стоит переходить только если логика принятия решений (планирование траектории VFH) станет слишком ветвистой.
- `cv2.resize` с `INTER_NEAREST` **очень быстрый** (не интерполирует, а просто берёт ближайший пиксель), и для карты глубин это **оптимально** (не нужна гладкая интерполяция).

3. **Синхронизация кадров через frame_id (Time-stamping)**

• **Проблема**: `npu_seg_server` и `npu_depth_server` работают асинхронно. Если один обработал кадр №1, а второй — кадр №2, маска и карта глубины относятся к разным моментам. Наложение даст неверное расстояние.
• **Риск**: Ложные срабатывания защиты (робот думает, что препятствие ближе) или пропуск реального препятствия.
• **Наивное решение**: Привязывать оба результата к `frame_id` и отбрасывать несовпадающие. **Проблема**: если Seg = 15 FPS, а Depth = 30 FPS, вы искусственно занижаете FPS до 15 и тратите ресурсы Depth впустую.
• **Коррекция (стратегия скользящего окна)**: В `cv_ctrl.py` — словарь-буфер `depth_buffer = {frame_id: depth_map}`. Когда приходит маска с `frame_id = 100`, проверяем: есть ли в буфере `100`? Если нет — берём ближайший (`99` или `101`) с допуском `Δt`. Кадры старше `frame_id - 5` удаляются.
• **Дополнительно**: `frame_id` лучше делать **timestamp** (мс от старта), а не просто счётчиком — тогда `Δt` считается как `abs(seg_ts - depth_ts) <= 50` мс. **Δt** должен быть **адаптивным** к скорости робота: чем быстрее едет — тем меньше `Δt` (иначе защита от столкновений сработает поздно).
```python
# Пример простейшей логики в cv_ctrl.py
base_dt = 60 # мс при базовом/медленном движении
current_speed = get_current_robot_speed() # берем из контура управления (м/с)

# Адаптируем окно: чем выше скорость, тем жестче допуск
dynamic_dt = max(20, base_dt - int(current_speed * 50)) 

if abs(seg_ts - depth_ts) <= dynamic_dt:
    # Сливаем маску и глубину
```
